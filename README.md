# Система аутентификации для FastAPI

Гибкая и расширяемая система аутентификации и авторизации для **FastAPI**.  
Проект реализован в модульной архитектуре и может быть интегрирован с любой базой данных и ORM.  
В базовой конфигурации представлен протокол репозитория пользователей и его реализация на **SQLAlchemy**.

## Описание проекта

Проект состоит из двух частей:  
- **auth** — это гибкая библиотека системы аутентификации для **FastAPI**, которая спроектирована модульно и может быть интегрирована с любыми хранилищами данных и ORM.  
- **app** — пример реализации, где демонстрируется, как использовать библиотеку для аутентификации с конкретной реализацией на **SQLAlchemy**.

Библиотека предоставляет гибкость для адаптации под любые требования, включая возможность легко заменять компоненты, такие как ORM, хэширование паролей и Pydantic-схемы.  
Кроме того, она включает миксины для реализации моделей на **SQLAlchemy** (`auth.sqlalchemy_mixins.UserMixin`, `auth.sqlalchemy_mixins.RoleMixin`) или абстрактный класс с требуемыми полями (`auth.abstractions.UserModelTypeHint`) для интеграции с другими библиотеками.


## Ключевые компоненты системы аутентификации
### 1. Фабрика роутера для системы аутентификации
Фабрика роутера create_auth_router расположена в файле auth/api/v1/router.py и отвечает за создание маршрутов для: регистрации, входа в систему, обновления данных пользователя, удаление пользователя(мягкое), а также выход из системы(с инвалидацией токенов).

Гибкость фабрики позволяет:
- user_repository_dependency: подменять репозиторий пользователей, обеспечивая интеграцию с любым хранилищем данных или ORM.
- token_service: использовать любой сервис для создания и проверки токенов (например, JWT).
- schemas: передавать кастомные схемы Pydantic для каждого маршрута аутентификации, включая создание пользователя, вход, и обновление данных.
- password_hasher: подменить хэширование паролей, используя любой алгоритм хеширования.
- prefix: настраивать префикс для всех маршрутов, позволяя гибко менять URL-структуру.
- tags: добавлять теги к маршрутам для удобства в Swagger UI.

Дополнительно:
Все usecase-классы аутентификации (регистрация, логин, обновление пользователя, удаление, выход) реализованы как зависимости FastAPI.
Это позволяет:
- Гибко подменять конкретные сценарии (usecase) при тестировании с помощью app.dependency_overrides.
- Интегрировать собственные реализации usecase без изменения кода фабрики.
- Повысить тестируемость и изоляцию логики на уровне зависимостей.

Более подробное описание см. в докстрингах файла auth/api/v1/router.py.

### 2. Репозиторий пользователей
Система использует протокол репозитория пользователей — UserRepositoryProtocol, который определяет контракт для доступа к данным пользователей. Этот протокол находится в файле auth.ports.user_repository.

Протокол содержит методы для работы с данными, такие как получение пользователей по ID, email, создание, обновление, удаление, методы двустороннего маппинга orm объекта пользователя в доменную сущность User для проверки инвариантов и другие.

Реализация этого репозитория может быть адаптирована под любую ORM. В базовой конфигурации предоставлена реализация для SQLAlchemy в файле auth.adapters.sqlalchemy.user_repository.py с классом SQLAlchemyUserRepository, который реализует все методы протокола.

Это позволяет системе оставаться независимой от конкретной ORM, предоставляя возможность легко заменять её на другую в зависимости от потребностей проекта.

Чтобы использовать репозиторий в маршрутах, необходимо передавать функцию зависимости в фабрику роутера, которая возвращает объект класса репозитория с вшитой сессией и моделью пользователя. Пример:
```
def get_user_repository(
    session: AsyncSession = Depends(get_async_session),
) -> UserRepositoryProtocol:
    return SQLAlchemyUserRepository(
        session=session,
        user_model=UserModel
    )
```

### 3. Доменный корень: User

User — это доменная сущность, которая представляет корень агрегата для всех операций, связанных с пользователем в системе аутентификации. В User происходит:

Роль в проекте:
- Представление данных: класс User является центральной сущностью для данных пользователя в домене аутентификации и авторизации. Он инкапсулирует данные, связанные с пользователем, такие как его email, имя, статус активности и т.д.
- Проверка инвариантов: класс гарантирует соблюдение важных правил целостности данных (например, валидность email, активность пользователя), проверяя их при каждом изменении состояния.


### 4. Хэширование паролей: PasswordHasher

PasswordHasher — абстрактный класс для хэширования паролей, с методом hash для хэширования и verify для верификации пароля при входе в систему.
По умолчанию используется реализация PBKDF2Hasher, который использует алгоритм PBKDF2 с HMAC-SHA256 и соль размером 16 байт. Количество итераций по умолчанию — 200,000. Класс находится в файле auth.services.security.password.py. Эта реализация может быть подменена в фабрике роутера для использования другого механизма хэширования, если это необходимо для проекта.


### 5. Сервис работы с токенами: TokenService
TokenService — это stateless сервис для работы с JWT токенами, реализующий интерфейс TokenServiceProtocol.
Сервис предназначен только для создания и проверки токенов:
- provide_access_token — генерирует access token, который включает в себя sub (идентификатор пользователя) и token_version для аннулирования токенов.
- decode_access — декодирует токен и извлекает полезную информацию, включая sub (идентификатор пользователя), проверяя токен на истечение срока действия и другие временные метки.
Фабрика роутера не предполагает дефолтного объекта работы с токенами, т.к. сервис включает чувствительные данные - `secret`, потому нужно создать объект класса TokenService передав туда свой secret(можно и остальные параметры настроить) и передать в фабрику роутера.

## Реализация управления доступами в App
Авторизация и проверка ролей не входит в задачи библиотеки аутентификации, потому реализация на приложении, которое интегрирует в себя систему аутентификации.
В демонстрационной реализации приложения используется ролевое управление - RBAC во взаимодействии с permission_level у каждой роли для разграничения прав пользователей и возможности менять уровни доступа группе пользователей суперюзером. Проверка прав реализована через гибкие зависимости FastAPI, которые не смешивают загрузку ресурсов, одиночной проверки доступа или авторизацию. Примеры зависимостей:
- `require_min_permission_level` - фабрика, создающая зависимость, которая проверяет, что пользователь отправивший запрос имеет уровень доступа не ниже, чем трубется в эндпоинте. Уровень определяется динамически для каждого эндпоинта.
- `author_or_min_permission_level` - предоставляет доступ к ресурсу для автора или пользователя с соответствующим уровнем доступа. Также определяется динамически для каждого пользователя.
- `current_user_is_higher_than_target` - сравнивание уровней доступа двух пользователей, отправившего запрос и искомого. Для получения доступа, отправитель должен быть уровнем строго выше, чем целевой пользователь. Таким образом например, пользователь с более низким `permission_level` не сможет добавить или снять роль с пользователя с более высоким уровнем доступа. Также, пользователям не могут задать роль целевому пользователю выше или равной своей по уровню доступа, как и снять роль.
### Суперпользователь не подвержен этим ограничениям. У такого пользователя есть доступ к эндпоинту изменения `permission_level` у ролей.



## Развертывание проекта
1. клоинировать репозиторий и перейти в папку с проектом
```bash
git clone https://github.com/Keleseth/auth-system-fastapi
cd auth-system-fastapi
```

2. Создание файла .env
Создайте файл .env в корне проекта, используя пример из .env.example. Секцию тестовых пользователей лучше не менять.

3. Создание и запуск контейнеров
После того как файл .env создан, можно создать и запустить контейнеры с помощью Docker Compose:
```bash
docker-compose up -d --build
```
Команда соберет контейнеры и запустит все необходимые зависимости. Проект будет доступен по адресу: http://127.0.0.1:8001
API документация доступна по адресу http://127.0.0.1:8001/docs

4. Остановка работы приложения и контейров
```bash
docker compose down
```

## Тестовый эндпоинт для проверки работы авторизации:
- После запуска контейнеров и FastAPI приложения, в базе данных будут созданы 3 роли и 3 пользователя с ролями author, admin и moderator.
- API документация станет доступна по адресу http://127.0.0.1:8001/docs, где можно протестировать все эндпоинты с примерами запросов.
- Доступ к ресурсу по тестовому эндпоинту 127.0.0.1:8001/v1/chocolates/{id}(1-3) будет у пользователя автора и админа, модератору же ресурс не доступен с ошибкой 403. Для проверки работы эндпоинта нужно получить токен по адресу 127.0.0.1:8001/v1/auth/login предоставив почту и email из .env файла и использовать для тестового эндпоинта. См. документацию API.
### В папке postman_collection находится коллекция эндпоинтов для тестирования системы вручную, нужно будет добавлять токены самостоятельно.

4. Рефакторинг, добавление гибкости интегрирующим приложениям.
